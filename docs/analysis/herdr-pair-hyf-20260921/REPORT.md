# HYF herdr-pair 会话成本审计

结论：**确有必要优化 skill，第一优先级是规划者的上下文生命周期，其次是工单预检和每轮证据基线。** 本次有价值的规划、诊断、独立验收很多，不能把规划者调用都视为浪费；但从约 54 万 token 历史上下文开始配对、等五轮才压缩，是明显可避免的成本放大因素。缩短工单或取消独立验收都不是最先该做的事。

**审核复算已并入（第 9 节）：** 缓存整段重建与调用间隔的关系是确定性的——间隔 >5 分钟的 49 次调用中 46 次整段重写，≤5 分钟的 666 次中 0 次。按此模型归因，第一阶段估算费用约 172 计费单位中 **约 69% 来自进入配对前已携带的 54 万 tokens 历史**；若同样的调用序列把上下文压在 15 万以内，估算约 42。因此 P0 应拆成三条更具体的动作：`init` 前先压缩、派发后等待期间压缩、快照与台账作为二者的前提。

**费用补充已完成：** 9 月 20–21 日账单总扣费 206.677663；与本会话主模型逐条匹配的 370 笔为 167.958395，其中缓存创建和读取占 94.74%。这支持上述优先级。账单还有约 26.23 花在 301 笔仅输出 7–8 token 的 Sonnet 请求上，其来源待定位，不能直接归给 herdr-pair。详见第 8 节。币种在表中未注明，金额保留表内计费单位。

## 1. 统计口径

来源是 `/public/log/hyf`，不是消息中误写的 `/public/og/hyf`。本次只分析导出日志和文件，没有重新运行原项目的生物信息分析，也没有修改 skill。

- 会话共 4,813 行，从 9 月 17 日开始。用户首次明确调用 herdr-pair 在 JSONL 第 1924 行。此前已有开发、端到端验证与需求讨论。
- 1,453 条 assistant 记录包含同一调用的 thinking/text/tool_use 分块。按 `message.id` 去重，剔除 synthetic 后有 **716 次模型调用**；所有同 ID 记录的 usage 完全一致，脚本用断言核实。
- usage 分为普通输入、缓存写入、缓存读取、输出。thinking 是 output 的子项，不重复相加。累计输入是多次调用各自输入长度之和，不是独有上下文大小。
- “配对开始至推送”是第 1924–4717 行的时间窗口，**包含前端调研、用户问答、文案、环境诊断和提交工作，不等于九轮调度自身成本**。
- 缺少执行器完整会话和子代理完整 usage，不能算双方总成本或证明比单代理更便宜。第 1–7 节的 token 数字均为日志报告值；新增账单覆盖部分日期，其金额和逐条匹配结果见第 8 节。

## 2. 最大成本来源：用巨大的旧上下文做后续每一步

配对首次调用的输入长度是 **540,258 tokens**，不是从空白开始。第五轮结束前达到 **978,771**。压缩事件自报 preTokens=980,127、postTokens=25,544；压缩后首次可见模型调用的实际输入为 **67,827**，说明摘要之外仍有重新注入内容，不能拿 25,544 当后续完整调用长度。

| 指标 | 第一阶段 | 第二阶段 |
|---|---:|---:|
| 调用次数 | 187 | 204 |
| 单次输入中位数 | 729,376 | 185,482.5 |
| 单次输入平均数 | 759,019.7 | 202,981.4 |
| 累计输入（含缓存） | 141,936,690 | 41,408,196 |

第二阶段多了 17 次调用，累计输入却少约 **70.8%**。这是上下文体积有重大影响的直接迹象，但两阶段工作不同，不能称为受控实验，也不能承诺修改 skill 就节省 70.8%。

更关键的是：第一阶段有 **22 次单次缓存写入超过 10 万 tokens**，合计 **16,083,972**，占该阶段缓存写入 **97.63%**。这些调用距上一条可见 assistant 调用均超过五分钟；所有缓存创建记录均标为 `ephemeral_5m_input_tokens`。

**审核复算：这不是"相符"，而是确定性关系。** 把全部 716 次去重调用按"距上一次调用的间隔"分桶，以"本次缓存创建 > 本次上下文的 90%"判定整段重建：

| 距上一次调用的间隔 | 调用数 | 整段重建 |
|---|---:|---:|
| ≤2 min | 629 | 0 |
| 2–5 min | 37 | 0 |
| >5 min | 49 | **46** |

分窗口看，第一阶段 >5 分钟的 23 次中 22 次重建，第二阶段 8 次中 7 次，配对前 15 次中 14 次；三个例外各自带有约 11,688 的缓存读取（前缀命中）。日志虽无逐次 cache-miss reason，但 0/666 对 46/49 已足以把机制写成：**每次超过 5 分钟的等待都会让下一次调用按 6.25/M 重写整段上下文**。由此得到一个可预测的成本模型：

> 费用 ≈ 上下文长度 × (6.25 × 超 5 分钟间隔次数 + 0.5 × 调用次数) / 10⁶

在配对工作流里"等执行器超过 5 分钟"是结构性的、不可消除的，所以 skill 唯一能动的变量确实只有上下文长度——这与本节结论一致，但推导到此才闭合。费率来源见第 8、9 节。

**开局那 54 万到底占了多少。** 按第 8 节反推费率对第一阶段 187 次调用估算：合计约 **171.8** 计费单位，其中 22 次整段重建 ≈ 100.5、缓存读取 ≈ 62.7、输出仅 ≈ 6.1。把每次重建和读取中不超过 540,258 的部分归给"进入配对前已携带的历史"：重建 74.3 + 读取 44.6 ≈ **118.9，占第一阶段估算的 69.2%**。反事实：保持同样的调用序列和输出，只把每次读取/重建的上下文压在 150,000 以内，第一阶段估算约 **41.6**。第二阶段用同一方法估算为 37.51，与第 8 节账单实测 37.506 一致，说明费率和模型可用；第一阶段落在 9 月 18 日、不在账单内，其数字是外推值。复算见 [gap_audit.py](gap_audit.py) / [gap-metrics.json](gap-metrics.json)。

例子：执行器 r005 首次阻塞回报之后，规划者单次写缓存 958,762；下一次完成回报之后又写 968,043。用户暂停、等待执行器、跨天继续，都会让维持超大上下文的策略变得昂贵。**这不是反复轮询造成的主要问题**：日志中显式 Herdr 状态/屏幕检查只有少数，没有持续高频轮询的证据。

证据：[首次配对调用](/public/log/hyf/session-63ae5e07-20260921.jsonl:1926)、[大缓存重建](/public/log/hyf/session-63ae5e07-20260921.jsonl:3270)、[压缩元数据](/public/log/hyf/session-63ae5e07-20260921.jsonl:3367)。

## 3. 哪些开销合理，哪些可以压缩

**实际工作量很大，Planner 不是只做派单。** 配对期间仍有需求更改、前端仓库调研、接口答复、说明文档作者工作，以及同源比对的实质诊断。九轮 accepted 也不代表九次一遍通过：r003 出现失败测试，r005 主动 BLOCKED，r006 两次纠正文案，r008 有多次边界澄清，都在同一轮里收敛后 accepted。

特别是压缩恢复至 r006 派发这一段，共 **79 次调用、54,271 输出 tokens**，含 r003–005 收尾提交、大区间小麦诊断、readme 编写和水稻运行环境排查。这些工作大部分不能靠减少派单格式消失。其中查找并纠正水稻数据库/配置的连续步骤已有 17 次调用；把正确命令、数据路径、物种和参考序列映射保存在可核验的环境记录里，能减少后续重找。

**独立验证有实际价值。** 日志可见三组有基线、突变失败、恢复通过的验证：

- r006：模板措辞、导航项和占位符三个突变均被测试抓到。
- r007：负链反向、互补、锚点及越界保护四个突变均被抓到。
- r008：zip 原子写入、输出位置和 readme 三个突变均被抓到。

这些比多跑一遍同样的绿测试提供更多新证据，应保留高风险场景的此类验证。[r006 输出](/public/log/hyf/session-63ae5e07-20260921.jsonl:4005)、[r007 输出](/public/log/hyf/session-63ae5e07-20260921.jsonl:4192)、[r008 输出](/public/log/hyf/session-63ae5e07-20260921.jsonl:4480)。导出 README 把负链突变写到 r009，实际发生在 r007。

**工单不是最大头，但确有过度指定实现和重复解释。** 九次初次写工单的整次调用共输出 50,906 tokens（包含 6,068 thinking 和伴随文字，不是纯工单 token），占配对窗口输出约 12.24%。所以压短工单有收益，但不足以解释或解决全部高消耗。

r009 工单同时解释模块查找、逐条预判 mock 是否失效，还出现 FIELDS “留在 homology”与“定义在 blastdb”的矛盾句。mock 预判被执行器纠正。这类地方适合写清“保持哪些行为、允许哪些文件、如何验证”，让执行器按真实依赖调整 import/patch，不必由 Planner 先完整演算实现细节再让 Executor 演算一遍。[工单](/public/log/hyf/handoffs/round9-split-blastdb.md:58)

同样不能用“只相信执行器报告”替代 Planner 验收。建议减少的是**无新增证据的重复操作**，不是取消责任。

## 4. 五处工单问题之外，本次还能看到什么

**范围和验收缺少统一预检。** r001 已有“显式允许的文件恰为 untracked、又禁止所有 untracked”的冲突；r003 测试路径受影响却被禁止修改；r008 要改线程参数却禁止 homology.py，又没有预先允许日志目录；整文件 lint 与局部修改 fence、历史债务之间也没有提前约定。不是执行器“爱问问题”，而是执行契约本身不可同时满足。

澄清必须保留，但可通过派发前检查降低次数：edit/create/forbid 是否交叉，必要测试和日志目录是否允许，基线 lint 是否已失败，修改是否触碰项目行数上限。验收可以合理覆盖 fence 之外的文件，关键是区分“允许检查的范围”和“允许修改的范围”，并明确历史失败的处理。

**第九轮是上轮授权缺漏引出的补救工作。** 工单直接承认 402 行来自 Planner 追加线程参数时未核对 400 行限制。本轮窗口共 15 次调用、14,809 输出 tokens。拆模块本身有结构价值，不能把整个成本都算浪费；但若在 r008 授权时核对约束，可以减少独立补救轮次及额外交接。[r009 背景](/public/log/hyf/handoffs/round9-split-blastdb.md:26)

**独立验收的基线不够准确。** r009 Planner 用 `git show HEAD:...` 对比拆分后源码；但前几轮有未提交改动，所以输出显示 run_blastn 不一致、多个保留定义也不同。随后口头归因为以前已验收的改动。这个检查有参考价值，却没有机械证明“相对本轮开始前逐字不变”。执行器报告称保存了本轮前副本并验证；导出只有报告，未包含那些副本和验证脚本，因此本审计不能独立重验该断言。应让 Planner 在派发前保存本轮真实工作区快照，验收使用同一快照，而不是用旧 HEAD 后再凭上下文解释。[对比命令与结果](/public/log/hyf/session-63ae5e07-20260921.jsonl:4559)、[执行器基线说明](/public/log/hyf/executor-reports/round9-report.md:8)

**台账比叙述可靠，但台账缺少重要信息。** 所有轮次 `artifacts` 和 `notes` 为空，未持久化澄清、修订后的 fence 和验收证据。CHECKPOINT 仍保留 r008 禁止 homology.py 的原始范围。Planner 最终还说“阶段 2 五轮已满”，实际 state 中是四轮；把“七处 patch + 两处 import”复述成“五处 patch + 两行 import”。这些不是实现失败的证据，但说明长篇口头复述不应承担计数和恢复状态的职责。

## 5. 自动压缩与恢复：有用，但还不完整

实际路径可证：第五轮结束 → 排队 compact → 约 155 秒完成压缩 → watcher 发 auto-continue → Planner 检查 state → Planner 自行执行 rollover。压缩结束时 state 仍是 phase=1、rollover_required=true，直到第 3414 行显式 rollover 才推进。

因此本次证明了 **watcher + Planner 补偿能自动续跑**，没有证明文档所说的 SessionStart 自动 rollover 在该环境生效。另有 context-mode 的缺失脚本错误，但不能直接归因为 pairctl hook 的失败，两者应分开。

更值得改的是恢复材料：首次调用加载的 skill 有 **923 行、61,451 bytes**；压缩后宿主只重新注入前 **20,000 字符**，刚好在 §3 工单规则之前截断，后面的验收、环境和执行器规则都不在这份恢复副本里。短核心协议比“在大文件末尾再加一条规则”更可靠。[完整历史 skill](session-skill-snapshot.md)、[压缩后副本](session-skill-after-compact.md)

审核补充：当前仓库版本 `skills/herdr-pair/SKILL.md` 为 989 行、约 57 KB，仍远超这一上限；`claude_session_start_hook.py` 注入检查点的 `MAX_CONTEXT_CHARS` 为 16,000 字符。两条上限决定了“核心协议 + 检查点”必须一起控制在约 15 k 字符内，否则恢复上下文里进的仍是截断版。

与此相伴，r006–r009 导出工单中都没有重申 `/tmp` 禁令，Planner 的三组突变验证也实际用了 `/tmp/omsnp-mut*`。这是明确的执行偏离；**仅凭先后关系不能证明是压缩截断导致**。它说明规则文档很长并不保证关键规则被保留和执行。

当前仓库版本与本会话加载版本不同：仓库已多出 revision、ack-round、check-round 等契约机制，不能把旧版缺陷说成新版一定未修，也不应为了本次成本优化机械再叠加一套确认协议。上下文预算和有效基线仍应单独解决。

## 6. 优化优先级与具体改法

| 优先级 | 建议 | 本次证据对应的收益 |
|---|---|---|
| P0-a | **`init` 前先压缩**：Preflight 加硬规则——上下文超过阈值（或会话已跨天）就先 `/compact` 或 `/clear`，再开始配对。这是实现成本最低的一条。 | 直接对应第一阶段估算中 69% 的费用（约 119/172）；不需要任何新机制。 |
| P0-b | **把压缩节奏改成"派发后、等待期间"**，五轮只作后备。每次 `send-round` 之后规划者必然要等执行器 >5 分钟，缓存无论如何会失效，此时压缩在缓存上是零成本的。Claude 规划者的用量可由 pairctl 读取（见第 9 节），拿不到 usage 的规划者用这一条不依赖 usage 的触发；不猜数字。 | 本次五轮跨了 2.5 天、上下文涨了 44 万，轮数作为触发条件几乎无效；按等待节奏压缩把每次重建的基数压到十几万级。 |
| P0-c | **先整理恢复契约，再提早压缩**：checkpoint 保存当前目标、用户决策、有效 fence/revision、工单与报告路径、基线快照路径、未完成验收和下一条命令；`finish-round --status accepted` 时 `--artifacts/--notes` 为空应 fail-closed。检查点变厚后以"指针 + 落盘文件"注入，受 hook 16,000 字符上限约束。活跃执行器回报与写入占用必须持续可识别。 | 当前 `write_checkpoint` 只有轮次表和后台任务，notes/artifacts 全空、范围修订丢在聊天里；P0-a/b 要提高压缩频率，这一条是前提，必须同一轮落地。 |
| P1 | **派发前轻量检查工单可执行性**：自动检查清单冲突、scratch 路径和机械行数约束；必要修改涉及哪些文件由 Planner 定向检查，不再泛读整个仓库。只在变化时更新环境命令记录。 | 降低 fence 冲突、历史 lint 争议、重新寻找运行参数和 402 行补救。 |
| P1 | **每轮保存真实工作区基线和验收账本**：`send-round` 已知 scope，把 fence 内 tracked/untracked 文件按 `round_id+revision` 复制到 state 目录，验收用 diff 对快照；旧 HEAD 只作为提交标识，不能代替 dirty 工作区的轮前状态。通过证据绑定快照，内容变更时失效。 | 消除 r009 比较旧 HEAD 后靠记忆解释的过程，让独立验收更强且更短。成本很低。 |
| P1 | **按风险安排独立验收**：Executor 执行规定检查，Planner 核实范围和关键行为；选用 cmp、AST、突变或独立重算解决具体风险。相同快照已通过的检查不因恢复上下文自动全部重跑。项目要求的检查仍须完成。 | 保留这次真正有收益的验证，减少重复 suite、重复数据探索、同一事实多轮复述。 |
| P2 | **把 skill 拆成短核心与按需参考**：核心保留角色、单写者、环境、派发/回报、暂停条件、基线和恢复要求；案例、内核 argv 上限原理、故障恢复细节按需读取。核心目标明确写成 **< 15,000 字符**（宿主回灌 20 k、hook 注入 16 k）。 | 核心能完整进入压缩后的恢复上下文，减少加载和理解成本；不是简单删字。 |
| P2 | **工单描述约束和结果，少预写实现推理**；稳定公共契约按版本引用并要求 Executor 读取，关键环境和 fence 仍随工单携带。长正文用固定版本文件或快照引用。 | 减少 Planner 重复实现、过度猜测 mock 行为；保持 fresh executor 的自包含性。 |
| P2 | **将修订、澄清和证据位置写入既有台账**，摘要和计数由工具生成；回报用简短结论与证据索引，原始完整日志保留落盘。 | accepted 不再掩盖过程中的阻塞，压缩后不靠聊天记忆重建范围。 |

不建议第一步就取消 Executor 每轮 fresh，也不建议把九轮强行并成少数大轮。本导出没有执行器 token 明细，无法量化每轮 fresh 的总代价；fresh 带来的重读可能存在，但不是本次 Planner 最大成本的已证实原因。

也不建议通过保持长上下文、定时发无意义请求来保缓存。缓存 TTL（5 分钟 / 1 小时）是宿主层的开关，不在 skill 控制范围内；它是否可配置应当作为事实去核实，而不是先行否定——但即便可用，它只改变重建次数，不改变基数，仍排在上下文长度之后。本报告不据此估算收益，也不为表外日期直接补算金额。

**更根本的结构问题**：规划者同时是用户的通用助手。前端调研、文档写作、环境排查这些一次性的大体积工具结果，全部沉积在需要长期存活的编排上下文里，再随每次重建被反复计费。除了压缩，把探索性调研交给子代理或另一个 pane、让规划者上下文只保留编排状态，是比"压得更勤"更根本的解法。本次日志无法量化这一项，列为方向而非承诺。

## 7. 下一次怎么判断优化有效

先只改变上下文预算、恢复摘要和工单预检，保留相同质量门槛。记录每次调用去重后的普通输入/缓存写入/缓存读取/输出、轮前上下文长度，以及工单修订原因。把工作区间区分成需求/诊断、派发、Executor 等待、验收和收尾，勿把用户跨天暂停计成执行器慢。

同时观察质量：规划工单导致的阻塞数、验收找到的真实缺陷、执行器纠正规划者的有效事实、恢复后重新探索次数、同一快照重复检查次数。不要把“零提问”或“零 rejected”设成优化目标。

本次支持的判断是：**质量责任设计值得保留，成本控制需要补上；先管理携带多少历史，再优化做多少次重复工作，最后才缩短工单文字。** 没有对照实验，不能给出可信的整体节省百分比。
