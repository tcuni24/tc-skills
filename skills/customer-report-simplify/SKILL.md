# 客户报告精简

技术团队写给客户的报告，最常见的失败方式不是「写错」，而是「什么都写了」。
本 skill 把一份数据正确但客户读不下去的报告，改成围绕客户问题组织、正文短、细节可查的版本。
适用于探针设计、测序分析、评估报告等任何「设计方 → 客户」的交付文档。

## 第一步：先诊断，不动手

用户通常先问「你觉得该怎么简化」。先给诊断和方案，得到认可再改。
把整份报告的纯文本抽出来看一遍（图片去掉、SVG 去掉），按下面五项逐项数：

1. **客户的问题是什么，报告用了几种指标回答它。**
   一个问题被四五种口径同时回答（不同分母、不同粒度、不同层级）时，客户分不清哪个是「答案」。
   数一下同一个核心数字在报告里出现了几次（页眉卡片、摘要、正文表、章节表、限制表）。
2. **分类体系叠了几层。**
   同一批对象用两三套命名（类型 / 子类型 / 设计来源 / 质量等级）各讲一遍，
   尤其是花整段篇幅解释「这个字段不代表什么」的，说明该字段根本不该进正文。
3. **术语和列名有没有直接进正文。**
   数据库列名、英文枚举值、希腊字母、统计术语、算法名（HMM、变点检测、N50、归一化）。
4. **有多少内容是在回应预期中的质疑，而不是回答问题。**
   「不是……而是……」「您无需就此决策」「为什么我们没有……」「这不是概率问题，是确定会发生的」。
   这些是给内部评审看的辩护，客户没有问。
5. **限制和注意事项放在答案之前还是之后。**
   「阅读前需要知道」式的前置免责会让客户在看到答案之前先看到一堆不确定性。

把诊断写成：问题 → 具体证据（出现次数、例句）→ 建议的新结构。方案要给到「哪一章保留什么、删什么、搬到哪」的粒度。

## 第二步：按客户的问题重排结构

正文只回答客户明确问的问题，加上客户必须做的决定。其它一切进折叠附录。
本项目验证过的骨架（4 个正文章 + 1 个文件章 + 1 个附录章）：

| 章 | 放什么 | 不放什么 |
|---|---|---|
| 01 一页结论 | 一句话答案；每个问题一张最小的表或三张卡片；客户唯一要确认的事 | 前置免责、方法说明 |
| 02 问题一 | 一句话定义指标；一张示意图解释指标怎么算；一张表；一两张全基因组级别的图；使用注意 | 其他口径、分母不同的对照数字 |
| 03 问题二 | 流程图；对象类型表（中文名）；判读方式示意图；四步操作清单 | 列名、枚举值、设计来源分类、质量等级 |
| 04 决策 | 决策表（客户情况 → 建议 → 原因）；两方案对比表；一张对比图；请客户反馈什么 | 论证用的中间数字、为什么某验证回答不了这个问题 |
| 05 文件 | 文件清单与校验值 | |
| 06 附录（全部折叠） | 分项统计与其他口径、设计流程、序列质量、验证细节、限制清单、字段对照表、术语表 | |

关键动作：

- **一个问题只留一种口径。** 选客户问句里的那一种（例：客户问「各有多少比例的区间」，就只用「1 Mb 区间覆盖率」）。其他口径进附录第一节，正文用一句话指过去。
- **合并判法相同的类型。** 两个类型如果分析时判法完全一样，正文里合并成一个，附录字段对照里再拆开。
- **「为什么有两版」只讲一次**，放在决策章。摘要里只放结论。
- **成对出现的 A/B 图**：正文只放直接回答问题的那一两张，其余进附录；纯 QC 图（GC、Tm、质量分级）只放一个版本，另一版一句「分布一致，图见 plot/」。
- **限制清单只保留影响客户操作的条目**在正文对应位置，其余进附录表。

## 第三步：写作规则

- 数字只放表格和图注。正文用「约九成」「约四分之一」。
- 术语第一次出现给中文解释；列名和英文枚举值只出现在附录「字段对照」表，表结构：正文说法 / 列名 / 取值 / 含义。
- 删掉所有防御性表述。判断标准：这句话是在回答客户的问题，还是在回答「你们为什么不……」。后者删。
- 限制和注意事项放在对应答案之后，用「使用时注意」而不是「阅读前需要知道」。
- 覆盖、密度、比例这类词容易和别的概念混淆（覆盖 vs 测序覆盖度），正文统一改成客户问句里的说法（「能确认身份的区间比例」）。
- 每个示意图回答一个问题：指标怎么算、对象怎么分、流程有几步。文字标签用中文名，不用代码。
- 图表配色沿用交付图（本项目：蓝 = AK58 / A 版，橙 = 节节麦 / B 版），示意图不用红色。

## 第四步：不覆盖原报告

用户几乎总会说「保留目前的结果」。做法：

- 内容层新开一个文件与原文件并列（例：`at100k_delivery_content_simple.py`），不改原文件。
- 渲染器**不要复制一份**。给现有渲染器加 `--content` 和 `--out-dir` 两个可选参数，默认值等于旧行为；
  非默认输出目录时从默认目录复制数据文件和图表目录，只签发新目录自己的校验清单，不碰内部留底。
  用户对「为什么有两个新文件」是敏感的：一个新内容文件 + 渲染器的小改动，比复制渲染器更容易被接受。
- 折叠附录如果渲染器不支持，加一种 `collapse {summary, blocks[]}` 块类型，用 `<details>` 包任意已有块，并补几行 CSS 放大 summary 字号。
- 生成到 `delivery/<日期>/<原目录名>-simple/`，和原目录并列，方便对照。

## 第五步：验证

无头浏览器通常不可用，所以验证靠脚本和结构检查：

```bash
python3 ~/.agents/skills/customer-report-simplify/scripts/audit_report.py <报告.html> \
    [--appendix-id sec-appendix] [--extra-terms 内部词1,内部词2] [--terms-file 词表.txt] [--strict]
```

脚本输出：正文（附录之前）字数、缺图占位数、内嵌图数、折叠块列表、违禁术语（阻断项，退出码 1）与可读性建议术语（非阻断项，退出码 0；--strict 时阻断）。
目标：违禁术语命中数为 0；缺图为 0；正文字数约为原报告的 1/4 到 1/3。特定项目词表可使用 `--terms-file`（如探针项目传 `references/probe-terms.txt`）。

再手工确认：

- 原目录的报告和校验清单时间戳没变。
- 默认参数的渲染命令 `--help` 仍正常，不要真的跑默认参数（会覆盖原报告）。
- 新画的 SVG：按「CJK 字符数 × 字号 + 半角字符数 × 字号 / 2」估算每行文字宽度，不能超过所在框宽或 viewBox 右边界。放不下就缩字号或改起点，不要挤。
- 示意图里的例子要和文字一致（例：示意 12 段里画了 9 个橙点、7 个蓝点，文字就写 9 和 7）。

## 交付时怎么说

汇报里写清：新文件在哪、原目录没动、生成命令、新结构一张表、自动检查的结果、哪些没做（没有新图、没有像素级验证）。
不要把诊断过程再讲一遍。
